4주차 — TypeScript 기초

단계 1의 마지막 주입니다. TypeScript는 새 언어가 아니라 JS에 “타입”을 덧붙인 것입니다. 지금까지 짠 JS는 전부 그대로 유효합니다. 실무 React Native 프로젝트는 대부분 TS로 되어 있어, 채용 공고의 우대사항에 거의 항상 등장합니다.

이번 주 완료 기준
  • 변수·함수에 타입을 붙일 수 있다
  • interface로 객체의 모양을 정의할 수 있다
  • 옵셔널(?)과 유니온(|)을 쓸 수 있다
  • 타입 에러 메시지를 읽고 무엇이 잘못됐는지 파악할 수 있다
  • 제네릭이 “무슨 문제를 푸는 도구인지” 설명할 수 있다
  • M2 달성: JS/TS로 콘솔 프로그램을 스스로 작성할 수 있다

0. 실행 환경 준비

Node 24는 .ts 파일을 그냥 실행할 수 있습니다(타입 표기만 떼어내고 돌리는 방식). 먼저 이게 되는지 확인하세요.

cd ~/Desktop/studyApp
echo 'const msg: string = "TS 안녕"; console.log(msg);' > check.ts
node check.ts

TS 안녕이 나오면 실행 준비 끝입니다. 다만 이 방식은 타입을 검사하지는 않고 떼어내기만 합니다. 타입 검사는 별도 도구가 합니다.

npm init -y                 # package.json 생성 (한 번만)
npm install -D typescript   # 타입 검사기 설치
npx tsc --init              # tsconfig.json 생성 (설정 파일)

npx tsc --noEmit            # 타입 검사만 실행 ← 이게 핵심 명령어
💡 두 명령의 역할이 다릅니다
  • node 파일.ts — 실행해서 결과를 본다
  • npx tsc --noEmit — 타입이 맞는지 검사한다 (실행은 안 함)

VS Code를 쓰고 있다면 사실 저장할 때마다 에디터가 알아서 검사해서 빨간 밑줄을 그어줍니다. 그게 TS를 쓰는 가장 큰 이유이기도 합니다 — 실행하기 전에 잘못을 알려주는 것.

1. 왜 TypeScript인가

1주차의 함정을 기억하시나요? "42" + 1이 "421"이 되던 것.

// JavaScript — 실행해봐야 잘못된 걸 안다
function add(a, b) {
  return a + b;
}
add(3, 5);       // 8
add("3", 5);     // "35"  ← 버그인데 아무도 안 알려줌
// TypeScript — 쓰는 순간 빨간 줄
function add(a: number, b: number): number {
  return a + b;
}
add(3, 5);       // 8
add("3", 5);     // ❌ Argument of type 'string' is not assignable to
                 //    parameter of type 'number'.

핵심은 이것입니다. TS는 실행하기 전에, 코드를 쓰는 순간 잘못을 잡아줍니다. 프로그램이 커질수록 이 차이가 압도적으로 벌어집니다. “6개월 전에 짠 함수가 뭘 받는지” 코드만 봐도 알 수 있다는 것도 큽니다.

2. 기본 타입 붙이기

const name: string = "강";
let age: number = 30;
const isStudent: boolean = false;

const fruits: string[] = ["사과", "바나나"];      // 문자열 배열
const scores: number[] = [90, 85, 100];          // 숫자 배열

변수 이름 뒤에 : 타입을 붙이면 끝입니다. 그런데 실무에서는 이걸 거의 생략합니다.

const name = "강";          // TS가 알아서 string으로 추론
let age = 30;               // number로 추론

age = "서른";               // ❌ 타입을 안 썼는데도 에러가 난다!

TS는 대입된 값을 보고 타입을 스스로 알아냅니다(타입 추론). 그래서 변수에는 대체로 타입을 안 쓰고, 함수의 매개변수·반환에는 씁니다. 함수는 밖에서 뭐가 들어올지 TS가 알 수 없기 때문입니다.

⚠️ any는 최후의 수단 
let data: any = "아무거나";
data = 42;
data.어쩌구().저쩌구();     // 에러 안 남 — 실행하면 터짐

any는 “검사하지 마”라는 뜻입니다. 붙이는 순간 TS를 쓰는 이유가 사라집니다. 막힐 때 any로 덮고 넘어가고 싶은 유혹이 크지만, 그럴수록 나중에 터집니다.

정말 타입을 모르겠으면 unknown을 쓰세요 — “모른다. 그러니 쓰기 전에 확인해라”라고 강제합니다. 코드 리뷰에서 any는 거의 항상 지적됩니다.

3. 함수에 타입 붙이기

function greet(name: string): string {
  return `안녕하세요, ${name}님!`;
}
//            ↑매개변수 타입   ↑반환 타입

const double = (n: number): number => n * 2;    // 화살표 함수도 동일

function printLog(message: string): void {      // 반환이 없으면 void
  console.log(message);
}

void는 “아무것도 반환하지 않는다”는 뜻입니다. 2주차에서 return을 빠뜨리면 undefined가 나왔던 그 상황을, 이제는 의도한 것인지 실수인지 타입으로 구분할 수 있습니다.

반환 타입은 추론되므로 생략해도 되지만, 초보 때는 명시하는 편이 좋습니다. “내가 뭘 돌려주려 했는지”와 “실제로 돌려주는 것”이 다르면 TS가 즉시 알려주기 때문입니다.

4. interface — 객체의 모양 정하기

2주차에서 만든 할 일 객체를 떠올려 보세요. 그 “모양”에 이름을 붙이는 것이 interface입니다.

interface Todo {
  id: number;
  title: string;
  done: boolean;
}

const todo: Todo = {
  id: 1,
  title: "TS 공부",
  done: false,
};

const bad: Todo = {
  id: "1",           // ❌ string은 number에 넣을 수 없음
  title: "운동",
                     // ❌ done이 없음: Property 'done' is missing
};

한 번 정의하면 배열에도 함수에도 그대로 씁니다.

const todos: Todo[] = [ ... ];                 // Todo가 든 배열

function countDone(list: Todo[]): number {     // 2주차 과제 5에 타입을 입힌 것
  return list.filter(todo => todo.done).length;
}

이제 list.까지만 쳐도 VS Code가 id, title, done을 자동완성으로 보여줍니다. 오타를 낼 수가 없습니다. 실무에서 TS를 쓰는 가장 체감되는 이점입니다.

옵셔널 ? 과 유니온 |

interface User {
  name: string;
  age: number;
  nickname?: string;        // ? = 있어도 되고 없어도 됨
  role: "admin" | "user";   // | = 둘 중 하나만 허용
}

const u1: User = { name: "강", age: 30, role: "user" };            // ✅
const u2: User = { name: "김", age: 25, role: "manager" };         // ❌ role 값이 틀림

"admin" | "user"처럼 정해진 값만 허용하는 것을 유니온 타입이라고 합니다. 오타로 "Admin"이라고 쓰는 실수가 원천 차단됩니다. 실무에서 대단히 많이 쓰는 패턴입니다.

셀프 퀴즈 — 이 코드의 문제는? 
interface User {
  name: string;
  nickname?: string;
}

function shout(user: User): string {
  return user.nickname.toUpperCase();
}

답: 'user.nickname' is possibly 'undefined'. 에러가 납니다.

nickname?은 없을 수도 있는 값입니다. 없는데(undefined) .toUpperCase()를 부르면 실행 중에 터집니다 — JS라면 사용자가 쓰다가 앱이 죽고 나서야 알았을 버그입니다.

해결은 “없을 경우를 처리했음”을 코드로 보여주는 것입니다.

if (!user.nickname) return "";
return user.nickname.toUpperCase();

// 또는
return user.nickname?.toUpperCase() ?? "";

TS는 if로 걸러낸 뒤에는 “여기선 값이 있구나”를 스스로 압니다(타입 좁히기). 잔소리처럼 느껴지지만, 실제 앱 크래시의 상당수가 정확히 이 undefined 문제입니다.

5. 제네릭 — 타입을 나중에 정하기

제네릭은 단계 1에서 가장 어려운 개념입니다. 지금은 “이런 게 있다” 수준으로만 알면 충분합니다. 뜻이 잘 안 와닿아도 괜찮으니 넘어가세요 — 실제로 필요해질 때 다시 오면 훨씬 쉽게 읽힙니다.

이런 상황을 생각해 봅시다. “배열의 첫 번째 요소를 돌려주는 함수”를 만들려고 합니다.

function firstNumber(list: number[]): number { return list[0]; }
function firstString(list: string[]): string { return list[0]; }
function firstTodo(list: Todo[]): Todo       { return list[0]; }
// ... 타입마다 하나씩? 끝이 없다

하는 일은 완전히 같은데 타입만 다릅니다. 그렇다고 any를 쓰면 결과 타입을 잃어버립니다. 여기서 “타입을 매개변수처럼 받는” 방법이 제네릭입니다.

function first<T>(list: T[]): T {
  return list[0];
}

const n = first([1, 2, 3]);            // n은 number로 추론됨
const s = first(["a", "b"]);           // s는 string
const t = first(todos);                // t는 Todo

<T>는 “타입 자리를 비워둔 것”입니다. 함수를 호출할 때 넘긴 값을 보고 TS가 T를 채웁니다. 변수가 값을 담는 상자라면, T는 타입을 담는 상자입니다.

T는 Type의 약자일 뿐 이름은 자유입니다. 직접 제네릭 함수를 만들 일은 당분간 없지만, 남이 만든 것을 쓸 일은 곧 생깁니다 — React의 useState<string>("")가 바로 제네릭입니다. 단계 2에서 만나면 “아, 그때 그거”가 되면 성공입니다.

todo.ts 파일을 만드세요. 2주차의 todo.js를 보면서 타입을 입혀 다시 작성하는 것이 과제입니다. (이번엔 참고해도 됩니다 — 목표가 “타입 붙이기”이므로.)

과제 5 — 우선순위로 거르기 (도전)

우선순위를 받아 그에 해당하는 할 일만 돌려주는 filterByPriority 함수를 만드세요. 매개변수 타입에 유니온을 그대로 써서, 잘못된 값을 넘기면 에러가 나게 하세요.

힌트

1단계: function filterByPriority(list: Todo[], priority: ???): Todo[]

2단계: ??? 자리에 "high" | "normal" | "low"를 그대로 쓸 수 있습니다.

3단계: 같은 유니온을 두 군데 쓰게 되죠? 이름을 붙여 재사용할 수 있습니다 — type Priority = "high" | "normal" | "low"; 그리고 두 곳 모두 Priority로 교체하세요. 이게 이 과제의 진짜 목적입니다.

🔒 5개 전부 다 한 뒤에 열어보세요 — 정답 & 해설

이번 주는 특히 에러 메시지를 직접 만나보는 것이 학습의 절반입니다. 일부러 틀린 값을 넣어보는 과정을 건너뛰지 마세요.

// todo.ts

type Priority = "high" | "normal" | "low";

interface Todo {
  id: number;
  title: string;
  done: boolean;
  priority: Priority;
  memo?: string;
}

const todos: Todo[] = [
  { id: 1, title: "TS 공부", done: true,  priority: "high", memo: "제네릭은 나중에" },
  { id: 2, title: "운동",    done: false, priority: "normal" },
  { id: 3, title: "장보기",  done: false, priority: "low",  memo: "우유, 계란" },
];

function printTodos(list: Todo[]): void {
  for (const todo of list) {
    const mark = todo.done ? "✅" : "⬜";
    let line = `[${mark}] (${todo.priority}) ${todo.title}`;
    if (todo.memo) {
      line += ` — ${todo.memo}`;
    }
    console.log(line);
  }
}

function countDone(list: Todo[]): number {
  return list.filter(todo => todo.done).length;
}

function filterByPriority(list: Todo[], priority: Priority): Todo[] {
  return list.filter(todo => todo.priority === priority);
}

printTodos(todos);
console.log(`${todos.length}개 중 ${countDone(todos)}개 완료`);
console.log("— 중요한 일 —");
printTodos(filterByPriority(todos, "high"));

왜 이렇게 되는가

  • type Priority를 따로 뺀 이유: 같은 유니온을 인터페이스와 함수 두 곳에 쓰기 때문입니다. 나중에 "urgent"를 추가하고 싶을 때 한 곳만 고치면 됩니다. 2주차에서 중복된 코드를 함수로 묶었던 것과 정확히 같은 사고방식입니다.
  • interface vs type: 객체 모양에는 interface, 유니온처럼 “값의 집합”에는 type을 쓰는 것이 흔한 관례입니다. 거의 바꿔 쓸 수 있으니 지금은 고민하지 마세요.
  • let line이 let인 이유: 메모가 있을 때 뒤에 덧붙이므로 값이 바뀝니다. 1주차의 “일단 const, 바꿔야 할 때만 let” 규칙이 여기서 실제로 판단으로 이어집니다.
  • if (todo.memo)의 역할: 화면 출력을 위한 조건이면서 동시에 TS에게 “여기선 memo가 확실히 있다”고 알려주는 역할을 합니다. 하나의 if가 두 가지 일을 합니다.
  • countDone이 한 줄이 된 것에 주목하세요. 2주차에는 let count = 0부터 시작해 7줄이었습니다. 3주차의 filter가 그 일을 대신합니다 — 배운 것들이 쌓여 코드가 짧아지는 순간입니다.
💼 취업 관점
  • TS는 채용 공고의 단골 우대사항입니다. 신입 지원자 중 TS를 “써봤다”고 말할 수 있는 사람은 생각보다 적습니다. 포트폴리오가 TS로 되어 있으면 그 자체로 차별점입니다.
  • any가 흩뿌려진 코드는 감점입니다. “TS를 쓴다면서 검사를 끄고 있는” 것으로 읽힙니다. 정 급하면 unknown + 타입 검사를 쓰세요.
  • “왜 TypeScript를 쓰나요?”는 면접 단골 질문입니다. “실행 전에 오류를 잡아주고, 자동완성으로 생산성이 오르며, 타입 자체가 문서 역할을 해서 협업에 유리하다” — 자기 경험을 곁들여 말할 수 있으면 충분합니다.
  • 단계 3부터 Expo 프로젝트는 TS로 시작하세요. npx create-expo-app이 TS 템플릿을 기본 제공합니다. 나중에 바꾸는 것보다 처음부터 TS로 가는 편이 훨씬 쉽습니다.

4주 동안 만든 결과물을 확인하세요. 커리큘럼이 요구한 “콘솔 미니 프로그램 3~5개”가 이미 채워져 있을 겁니다.

  • variables.js — 변수·조건문·반복문
  • todo.js — 함수·배열·객체
  • array-methods.js — 배열 메서드
  • fetch-user.js — 비동기 & 실제 API 호출
  • todo.ts — TypeScript
